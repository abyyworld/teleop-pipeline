Autonomy for remote handling in hazardous environments

Decommissioning is done by remote operation because a human cannot be in the room. The labour is not expensive, it is unavailable at any price. Autonomy would change that, and the thing standing in the way is not capability. It is that nobody can demonstrate a policy is safe to run in a cell.

The gap

Every task in a sealed cell is performed by a person driving a manipulator through a screen, slowly, one operator to one machine. Dose limits cap the hours available absolutely, so automating this is not displacing a worker. It is creating capacity that does not otherwise exist.

There is no accepted evidence standard for when a learned policy may run in that setting, and almost no real-hardware data to build one from. This work is an attempt at both: collect demonstrations from the operation that is already happening, and prove policy quality to a standard a regulator could accept.

The first result is a negative one

A behaviour-cloning policy trained on the pipeline below beats the obvious baselines by about four times. It also loses to the least clever baseline there is, which is repeating the previous action, at every point across the prediction horizon.

PredictorChunk MAE (rad)What it is
repeat last action0.01255Free. No model.
trained policy0.01582Behaviour cloning with action chunking.
training-set mean0.06670Free. Exploits directional bias only.
command no motion0.07261The floor.

This is the point, not an embarrassment. The same number reported without a persistence baseline would have looked like a working policy. Most published action-error figures in robot learning are reported against nothing. The evaluation here refuses to let that happen, and it refuses in the direction that costs me something.

The result above is on simulated data, where trajectories are smooth and repeating the last command is close to unbeatable. On real teleoperation the operator makes discrete decisions and persistence should break at the transitions. Whether a policy wins there is an open question, and answering it on real hardware is the next piece of work rather than something to assert now.

What is built

Nine repositories, all public, all runnable from a clean clone on generated data so none of it requires lab access to assess. Three of them exist because a result came back negative and was published anyway.

  • teleop-pipeline 6,777 lines · 102 tests

    Raw operator sessions in, a schema-checked, resampled, quality-scored and content-addressed corpus out, with every trained policy traceable to the exact bytes it was trained on. Nine quality metrics, each with a defect-injection test proving it catches what it claims.

  • vla-evals 2,494 lines · 42 tests

    Paired evaluation with McNemar exact tests and bootstrap confidence intervals. Refuses to declare a winner the evidence cannot resolve, and prints the smallest effect the sample could have detected when it finds nothing.

  • edge-policy-runtime 4,284 lines · 89 tests

    Signed over-the-air policy delivery with an on-device pre-flight health gate that refuses to run a bundle failing its checks or its signature.

  • robot-fleet-loop 4,639 lines · 93 tests

    The return path: telemetry, failure triage, retraining, canary and rollback, with a gate that can actually say no.

  • interactive-correction-for-manipulation 9,533 lines · 57 tests

    What it costs when a human correction is credited to the wrong part of a trajectory, and how often that happens.

  • isaac-grasp-scaling 7,146 lines · 131 tests

    Does a grasping network's orientation failure survive more data, or was the dataset simply too small? Answered rather than assumed.

  • simulated-grasping 7,147 lines · 113 tests

    Grasping in simulation, including what it takes to train one without a GPU and what that costs in precision.

  • ros2-grasp-latency 10,159 lines · 29 tests

    How much end-to-end latency writing a ROS 2 grasp node in Python actually costs, measured rather than argued about.

  • erl-semantic-mapping 1,544 lines · 36 tests

    Semantic occupancy mapping with an evaluation harness that gates on its own assumptions.

The app

The whole pipeline also runs as a desktop app, for the case where you are standing at a rig rather than sitting at a terminal. A button per stage, a live log, and the results. It leads with whether the policy beats the baselines and says so in the red case as plainly as the green one.

PyTorch is bundled, which is where the size goes. Nothing else to install. A machine with a GPU should install the package instead and get the GPU build.

Your browser will warn you, and it is right to

These binaries are not code-signed, because a signing certificate costs money this project does not yet spend. Chrome, Windows SmartScreen and macOS Gatekeeper all treat an unsigned executable as suspect. That warning is about a missing certificate, not about anything found in the file, but you should not take that on faith from a web page either. Check it instead:

  • Compare the hash. Every release ships a SHA256SUMS file. Run shasum -a 256 <file> on macOS or Linux, or Get-FileHash <file> in PowerShell, and compare.
  • Check the provenance. Each binary carries a signed attestation tying it to the workflow, repository and commit that produced it. gh attestation verify <file> --repo abyyworld/teleop-pipeline confirms that cryptographically.
  • Or skip the binary. pip install -e ".[dev,all]" from a clone, then teleop-pipeline studio. Same app, built on your machine from source you can read.

On macOS, keeping the file still leaves it quarantined, so it needs xattr -d com.apple.quarantine ./teleop-studio-macos-arm64 once before it will run.

What is not true yet

Stated here rather than buried, because the entire method being proposed is refusing to report a number that cannot be defended.

  • No real-hardware result. Every figure on this page comes from simulation or generated data.
  • No users. Nobody outside the project has run any of it.
  • No revenue, no pricing, no letters of intent.
  • No operator interviews yet. The choice of which task to automate first is a hypothesis, not a finding.
  • One person. Finding a second is an explicit milestone, not an afterthought.

The next piece of work is one task, one real manipulator, demonstrations collected through the existing recorder, a policy trained on them, and a paired evaluation against the operator baseline. Published whichever way it goes. That needs about a month of lab time and no capital.
