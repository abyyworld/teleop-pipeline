Autonomy for remote handling in hazardous environments

Decommissioning is done by remote operation because a human cannot be in the room. The labour is not expensive, it is unavailable at any price. Autonomy would change that, and the thing standing in the way is not capability. It is that nobody can demonstrate a policy is safe to run in a cell.

By abyyworld. One person, in progress.

§ 1

The gap

Every task in a sealed cell is performed by a person driving a manipulator through a screen, slowly, one operator to one machine. Dose limits cap the hours available absolutely, so automating this is not displacing a worker. It is creating capacity that does not otherwise exist.

There is no accepted evidence standard for when a learned policy may run in that setting, and almost no real-hardware data to build one from. This work is an attempt at both: collect demonstrations from the operation that is already happening, and prove policy quality to a standard a regulator could accept.

§ 2

The first result is a negative one

A behaviour-cloning policy trained on the pipeline below beats the obvious baselines by about four times. It also loses to the least clever baseline there is, which is repeating the previous action, at every point across the prediction horizon.

The point

This is the point, not an embarrassment.

The same number reported without a persistence baseline would have looked like a working policy. Most published action-error figures in robot learning are reported against nothing. The evaluation here refuses to let that happen, and it refuses in the direction that costs me something.

The result above is on simulated data, where trajectories are smooth and repeating the last command is close to unbeatable. On real teleoperation the operator makes discrete decisions and persistence should break at the transitions. Whether a policy wins there is an open question, and answering it on real hardware is the next piece of work rather than something to assert now.

§ 3

What is built

Nine public repositories, all runnable from a clean clone on generated data, so none of it needs lab access to assess. Three exist because a result came back negative and was published anyway.

  • teleop-pipeline 136 tests

    Raw operator sessions in, a schema-checked, resampled, quality-scored and content-addressed corpus out, with every trained policy traceable to the exact bytes it was trained on.

  • vla-evals 42 tests

    Paired evaluation with McNemar exact tests and bootstrap confidence intervals. Refuses to declare a winner the evidence cannot resolve.

  • edge-policy-runtime 89 tests

    Signed over-the-air policy delivery with an on-device pre-flight health gate that refuses to run a bundle failing its checks.

  • robot-fleet-loop 93 tests

    The return path: telemetry, failure triage, retraining, canary and rollback, with a gate that can actually say no.

  • interactive-correction-for-manipulation 57 tests

    What it costs when a human correction is credited to the wrong part of a trajectory, and how often that happens.

  • isaac-grasp-scaling 131 tests

    Does a grasping network's orientation failure survive more data, or was the dataset simply too small?

  • simulated-grasping 113 tests

    Grasping in simulation, including what it takes to train one without a GPU and what that costs in precision.

  • ros2-grasp-latency 29 tests

    How much end-to-end latency writing a ROS 2 grasp node in Python actually costs, measured rather than argued about.

  • erl-semantic-mapping 36 tests

    Semantic occupancy mapping with an evaluation harness that gates on its own assumptions.

§ 4

The app

The pipeline also runs as a desktop app, for standing at a rig rather than sitting at a terminal. A button per stage, a live log, and the results. It leads with whether the policy beats the baselines, and says so in the red case as plainly as the green.

  • macOS Apple silicon, 220 MB teleop-studio-macos-arm64
  • Windows x86-64, 218 MB teleop-studio-windows-x86_64.exe
  • Linux x86-64, 331 MB teleop-studio-linux-x86_64

Your browser will warn you, and it is right to

The binaries are not code-signed, because a certificate costs money this project does not yet spend. That warning is about a missing certificate, not about anything found in the file, but you should not take that on faith from a web page either. Three ways to check:

  1. Compare the hash against the SHA256SUMS file in the release.
  2. Check the provenance. Run gh attestation verify <file> --repo abyyworld/teleop-pipeline against the signed build provenance.
  3. Or skip the binary and install from source with pip.

macOS also needs xattr -d com.apple.quarantine ./teleop-studio-macos-arm64 once.

§ 5

What is not true yet

Stated plainly rather than buried, because the whole method is refusing to report a number that cannot be defended.

  • No real-hardware result. Every figure here comes from simulation or generated data.
  • No users. Nobody outside the project has run any of it.
  • No revenue, no pricing, no letters of intent.
  • No operator interviews yet. The choice of first task is a hypothesis, not a finding.
  • One person. Finding a second is an explicit milestone, not an afterthought.

The next piece of work is one task, one real manipulator, demonstrations collected through the existing recorder, a policy trained on them, and a paired evaluation against the operator baseline. Published whichever way it goes. About a month of lab time and no capital.
